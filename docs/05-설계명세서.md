# 영수증 소비 재판소 - 시스템 설계 명세서 (v2 — FastAPI 확정판)

> 원본: 팀 작성 (8/28 새벽). v2 수정: 스택 FastAPI 치환, 판정 룰 폴백 버그 수정, Bedrock 이유 생성 1곳 추가, 배포 8501 반영. 이 문서가 구현의 유일한 기준이다.

## 1. 설계 목표
하루 안에 MVP를 구현하고 EC2까지 배포한다. 복잡한 아키텍처 금지.
1. 프론트-백엔드 빠른 개발  2. 명확한 REST API  3. 동일한 변수명  4. SQLite 단일 파일 DB
5. EC2 배포 단순화  6. 분석 로직은 백엔드에서 일관 처리  7. 판결·유형은 항상 동일한 규칙
8. MZ 리액션 콘텐츠를 쉽게 추가할 수 있는 구조

## 2. 확정 기술 스택
- **Frontend: 순수 HTML + CSS + JavaScript** (프레임워크·빌드 없음. fetch로 API 호출. FastAPI가 static/ 정적 서빙)
- **Backend: FastAPI (Python) + 내장 sqlite3**
- **AI: Bedrock Claude** — 판결문 "이유(reasoning)" 산문 생성 1곳만. 실패 시 템플릿 폴백. 로컬은 MOCK_AI=1
- **배포: EC2 + nohup + 포트 8501** (기존 streamlit 종료 후 점유)
- 상세 제약은 `.kiro/steering/tech-constraints.md` (자동 주입)

## 4. 데이터 계약 (프론트-백엔드 필드명 — 절대 동일하게)
```
TransactionType = "EXPENSE" | "TRANSFER"
Category = "DELIVERY_DINING" | "CONVENIENCE_STORE" | "CAFE_SNACK"
         | "GROCERIES" | "SHOPPING_HOBBY" | "OTHER"

Expense = { id, storeName, date, amount, category, transactionType,
            defendant, memo, needsReview, createdAt, updatedAt }
CreateExpenseRequest / UpdateExpenseRequest
  = { storeName, date, amount, category, transactionType, defendant?, memo? }
```
| 필드 | 타입 | 설명 |
|---|---|---|
| id | number | 고유 ID |
| storeName | string | 상호명 |
| date | string | 소비 날짜 (YYYY-MM-DD) |
| amount | number | 금액 (정수, 원) |
| category | Category | 6종 코드 |
| transactionType | TransactionType | 소비/이체 구분 |
| defendant | string | 피고인 이름 (10자 이내, 생략 시 "익명의 자취생") |
| memo | string | 미분류 내역 메모 (10자 이내, 기본 "") |
| needsReview | boolean | 예금주 이름만 있어 분류 못 한 건이면 true |
| createdAt/updatedAt | string | 생성/수정 시각 |

## 5. 날짜·금액 규칙
- 날짜는 항상 `YYYY-MM-DD` 문자열, 월 조회는 `YYYY-MM`. UTC 변환으로 하루 밀리지 않게 날짜 문자열 그대로 저장·비교.
- 금액은 정수(18000). `"18,000원"` 문자열 금지. 콤마·"원"은 화면 표시에서만.

## 6. DB 스키마
```sql
CREATE TABLE IF NOT EXISTS expenses (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  store_name TEXT NOT NULL,
  date TEXT NOT NULL,
  amount INTEGER NOT NULL,
  category TEXT NOT NULL,
  transaction_type TEXT NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```
DB는 snake_case, API는 camelCase — 변환은 백엔드(Repository 계층)에서. 프론트는 DB 컬럼명을 절대 모른다.

## 7. 카테고리 정의 (화면 라벨 ↔ 코드)
| 코드 | 화면 | 대표 소비 |
|---|---|---|
| DELIVERY_DINING | 배달·외식 | 배달, 식당, 치킨, 분식, 술집 |
| CONVENIENCE_STORE | 편의점 | 편의점 식사·간식·음료 |
| CAFE_SNACK | 카페·간식 | 커피, 디저트, 베이커리, 아이스크림 |
| GROCERIES | 식재료·생필품 | 마트, 식재료, 세제, 생활용품 |
| SHOPPING_HOBBY | 쇼핑·취미 | 의류, 게임, 굿즈, 문화생활, 온라인쇼핑 |
| OTHER | 기타 | 분류 곤란한 소비 |

## 8. 거래 유형
- **EXPENSE**: 실제 소비. 분석에 포함.
- **TRANSFER**: 이체·송금. DB에는 저장하되 **모든 분석·총지출에서 제외**.

## 9. API 설계 (Base: `/api`)
공통 응답: 성공 `{"success": true, "data": ...}` / 실패 `{"success": false, "error": {"code", "message"}}`
상태코드: 200/201/204 정상, 400 잘못된 입력, 404 없음, 500 서버 오류

### POST /api/expenses — 저장
요청: `{storeName, date, amount, category, transactionType}` → 응답: 생성된 Expense
### GET /api/expenses?month=YYYY-MM — 월별 조회
응답: Expense 배열 (날짜 내림차순)
### GET /api/expenses/{id} — 단건 조회
### PUT /api/expenses/{id} — 수정 (요청 형식은 POST와 동일)
### DELETE /api/expenses/{id} — 삭제 → `{"success": true}`
### GET /api/analysis?month=YYYY-MM — 월 분석 (아래 §12 응답 전체)

## 10. 입력 검증 (위반 시 400)
- storeName: 빈 문자열·공백만 금지, 최대 100자
- date: `YYYY-MM-DD` 형식
- amount: 정수, 1 이상
- category: 6종 코드 외 거부 / transactionType: EXPENSE·TRANSFER 외 거부
- defendant: 선택. 문자열, 최대 10자 (초과 시 400, 조용히 자르지 않는다)
- memo: 선택. 문자열, 최대 10자 (초과 시 400)

## 11. 분석 규칙 (transactionType=EXPENSE만 대상)
- totalExpense = 금액 합 / paymentCount = 건수
- averagePaymentAmount = total ÷ count (count 0이면 0)
- 카테고리별 금액·건수·비율(소수 둘째 자리) = categoryAmount ÷ total × 100
- topCategory: 금액 최대 → 동률 시 건수 → 그래도 동률이면 카테고리 고정 순서
  (DELIVERY_DINING → CONVENIENCE_STORE → CAFE_SNACK → GROCERIES → SHOPPING_HOBBY → OTHER)
- largestSingleExpense: 최대 단일 지출 (없으면 null)
- **소액 결제 기준: amount ≤ 5,000** → smallPaymentCount (5,000 포함, 5,100 미포함)

## 13. 소비 유형 판정 규칙 (서버 룰, AI 판정 금지 — 우선순위 순서대로 첫 매칭)
1. **티끌 과소비형**: paymentCount ≥ 10 AND smallPaymentCount/paymentCount ≥ 0.5
2. **편의점이 내 부엌형**: CONVENIENCE_STORE 건수 ≥ 8 AND 전 카테고리 중 건수 1위
3. **냉장고보다 배달앱형**: DELIVERY_DINING 비율 ≥ 40%
4. **소확행 충전형**: CAFE_SNACK 비율 ≥ 30% AND DELIVERY_DINING 비율 < 40%
5. **취향에 진심형**: SHOPPING_HOBBY 비율 ≥ 30%
6. **야무진 자취생형**: GROCERIES 비율 ≥ 30%
7. **균형 생존형**: **위 1~6 어디에도 해당하지 않으면 무조건 이 유형 (폴백 — 조건식 없음)**
   ※ v2 수정: "최고 비율 < 30%" 조건을 제거. 판정 결과가 없는 입력이 존재하지 않도록 7번은 항상 폴백.
- 분석 대상 0건이어도 균형 생존형 + 화면 안내 "아직 판결할 소비가 없습니다."

## 14. 판결문 생성 규칙 (하이브리드)
- **crime / verdict / sentence**: 유형별 템플릿 배열에서 선택 (룰 기반, AI 아님)
- **reasoning(이유)**: **Bedrock Claude로 생성** — 통계 수치(총지출·비율·건수)를 프롬프트에 주입해 재판부 판단 2~3문장. 반드시 수치 1개 이상 인용. 호출 실패 시 템플릿 폴백 문장 사용. `MOCK_AI=1`이면 고정 문장.
- 템플릿 구조:
```
JudgmentTemplate = { consumerType, crimes[], verdicts[], sentences[], fallbackReasonings[] }
```
예 (DELIVERY_APP): crimes ["냉장고 유기죄","주방 방치죄","배달앱 상습 이용죄"] /
verdicts ["냉장고는 가구가 아닙니다.","주방이 울고 있습니다.","당신의 식사는 현관 앞에서 완성되고 있습니다."] /
sentences ["다음 달 배달은 주 2회 이하로 제한합니다.","최소 주 1회는 직접 장을 보십시오.","이번 달에는 냉장고를 최소 3번 이용하십시오."]

## 15. MZ 리액션 시스템
- 서버 관리: `reactionMessages: dict[consumerType, list[str]]` — 유형당 최소 10개, 권장 15개 (7유형 × 15 = 105개)
- 서버가 최종 유형의 배열에서 **랜덤 1개**를 골라 응답에 포함. 프론트는 랜덤 계산 안 함.
- 스타일 허용: ㅋㅋ/ㅎㅎ/ㄹㅇ/밈/짧은 문장/가벼운 놀림/과장/이모지
- 금지: 개인 공격, 외모·체형·건강·질병·장애 비하, 심한 욕설, 혐오, 집단 비하. 놀림 대상은 오직 "소비 습관".
- 예시 (원본 문서의 유형별 예시 전부 유효 — DELIVERY_APP "냉장고: 나도 좀 써줘...", CONVENIENCE_STORE "편의점이 아니라 거의 네 부엌인데?", CAFE_SNACK "커피 한 잔이 별거 아니긴 하지. 그게 27잔이면 얘기가 다르지 ㅋㅋ", SHOPPING_HOBBY "취향은 존중합니다. 통장도 좀 존중해주세요.", GROCERIES "자취생의 정석 발견.", OTHER "분류는 못했지만 소비는 확실하게 했네.", BALANCED "통장이랑 사이좋게 지내고 있군." 등)

## 16. 프론트엔드 화면 (페이지 3개)
1. **메인/입력**: 로고·소개·입력 폼(상호명/날짜/금액/카테고리/거래유형/저장)
2. **소비 내역**: 월 선택·총지출·내역 리스트·수정·삭제·[분석하기]
3. **분석 결과** (핵심 화면): 총지출 → 카테고리별 → 통계 → **판결문(죄명/증거/판결/이유/형량)** → **소비 유형 배너** → 배너 클릭 시 MZ 메시지 박스
- 중요도: 유형 > 판결문 > 총지출 > 카테고리 > 세부 통계

## 17. 책임 분리
- Frontend: UI·API 호출·로딩·에러 표시·결과 렌더. **분석 계산 금지, 유형 재계산 금지** (RULE 001/007)
- Backend: 검증·CRUD·통계·TRANSFER 제외·유형 판정·판결문(+Bedrock 이유)·MZ 선택

## 18. 구현 RULE (원본 유지)
- RULE 001 프론트는 분석을 직접 계산하지 않는다
- RULE 002 필드명 임의 변경 금지 (storeName을 shopName 등으로 X)
- RULE 003 카테고리 코드 동일 (DELIVERY_DINING — delivery/food 등 X)
- RULE 004 거래 유형 동일 (EXPENSE/TRANSFER)
- RULE 005 금액은 숫자로 전송
- RULE 006 프론트는 DB 직접 접근 금지, 항상 REST API
- RULE 007 분석 로직은 백엔드 한 곳에서만

## 19. 빈 데이터·보안
- EXPENSE 0건: total/count/small=0, largest/top=null, 유형=균형 생존형
- 로그인 없음·개인정보 미수집. 입력값 검증은 서버가. DB 파일 정적 제공 금지.

## 20. 배포 (EC2)
```bash
# 서버에서 (appenv 파이썬 사용, 포트는 8501만 열려 있음)
appenv/bin/pip install fastapi uvicorn
lsof -ti:8501 | xargs kill -SIGTERM 2>/dev/null; sleep 3   # 기존 streamlit 종료
nohup appenv/bin/python -m uvicorn main:app --host 0.0.0.0 --port 8501 </dev/null >app.log 2>&1 &
curl -s -o /dev/null -w "%{http_code}" http://localhost:8501   # 200 확인
```
접속: `http://18.135.105.80:8501` / API: `http://18.135.105.80:8501/api/...`
환경 변수: 서버에 AWS_DEFAULT_REGION 설정돼 있음. 추가 env 최소화. 로컬은 `MOCK_AI=1`.

## 21. 완료 시나리오 (원본 8개 유지)
S1 소비 입력→저장 / S2 이체 입력→저장되나 분석 제외 / S3 8월 분석=8월 EXPENSE만 /
S4 배달 40%+ → 냉장고보다 배달앱형 / S5 판결문(죄명·증거·판결·이유·형량) 반환 /
S6 유형 배너 클릭→MZ 메시지 / S7 수정→분석 반영 / S8 삭제→목록·분석 반영

## 22. 최종 원칙
재미 > 완성도 > 복잡한 기술. 사용자가 결과를 보고 웃고 친구에게 보여주고 싶어지면 성공.
이 문서에 정의되지 않은 기능(OCR·회원가입·계좌 연동·AI 학습)은 구현하지 않는다.
